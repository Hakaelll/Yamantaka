# PDF imagery on physical 3D books

The default native WGPU library now renders each visible document's first PDF
page onto the existing 3D book. The cover and a narrow image strip on the spine
follow the same physical volume. The existing pointer spring, lift, paper edges,
selection and reduced-motion behavior remain. Procedural jackets are fallback
presentation when an image is unavailable.

Flutter's connected `_ArtifactCoverImage` uses a file image with top-centered
cover fitting. This checkpoint restores that visual relationship in Rust. It
does not yet implement Flutter's automatic candidate scoring, manual source-page
selection or persistent small/large thumbnail cache.

| Before | After | Why |
| --- | --- | --- |
| Every document used a procedural jacket | Available PDF imagery replaces the jacket | Make books recognizable from their source documents |
| The spine used a procedural color | A darkened strip of the PDF image wraps onto the spine | Keep the binding related to the real cover |
| A textured quad interpolated across two triangles | A bounded 117-vertex image mesh follows the rigid projection | Reduce perspective distortion of source artwork and text |

## Execution and ownership

Visible books collect at most 16 distinct cover requests. The application actor
submits low-priority tickets to the existing PDFium owner; the UI performs no
file reads or PDF calls. Covers are at most 512 pixels on their longest side.
Their native RGBA buffers reserve tracked page memory before allocation. WGPU
uploads use the existing governed presenter and fence-bound texture ownership.
Off-screen slots are released and their pending requests cancelled. Results
must match the slot's cancellation identity, document and generation; painted
textures must also match the current path and fingerprint.

A temporary native document is dropped after extraction on success, failure or
cancellation. An already-open document can be reused without a new handle,
including a PDF the user has unlocked. Extraction never evicts a reader or
opens a third native handle. If both handles are occupied by other documents,
the request ends with a fallback rather than waiting indefinitely.

The alternate Glow compositor retains the procedural fallback until its cover
uploads have governed lifetime accounting. Missing, protected or failed PDFs
also retain a static fallback. Retry controls, durable cache invalidation,
manual cover selection and complete Flutter cover parity remain pending.

## Verification

- Full workspace: 408 tests passed. The new real-PDFium regression checks bounded
  pixels containing source content, cancellation, password failure, reader
  preservation, two-handle admission, existing-handle reuse and unchanged source
  hashes.
- Final UI: all 93 tests passed after the final presentation changes. The actor
  password regression also extracts a cover from the unlocked native handle and
  continues reading text before closing the reader.
- Workspace Clippy with warnings denied and format checks passed.
- Seven successful native captures show dark/light themes, Spanish, selection,
  tilt, reduced motion, compact 2× scale and the original textual PDF fixture.
  Each records installed native covers, zero pending cover replies and no more
  than 16 resident slots.
- Independent verification matched all 64 UI source hashes, Cargo.lock,
  executable, ten synthetic PDF fixture hashes, image/control hashes and
  unchanged published PNG pixel chunks.
- Executable SHA-256:
  `76E19E4A30088CEFD93D50BFD962EFFF1C3844CBD942C371A9CBB2268BEBAEC4`.

See [the manifest](../screenshots/rust-pdf-covers/capture-manifest.json) and
[the library capture](../screenshots/rust-pdf-covers/pdf-covers-dark.png).
The colored covers are pages of explicitly synthetic PDFs generated by
`tool/create_rust_cover_fixtures.py`, not images substituted into the UI.
No personal library was opened. Impeccable's detector returned no findings;
this does not establish native accessibility or visual acceptance.

Physical DPI, Narrator, rapid cataloguing interactions, large-library frame
times, device-loss behavior and whole-rewrite release acceptance remain pending.
Compilation used disabled development/test symbols after the requested cleanup;
the regenerated target cache measured about 1.98 GiB, rather than preserving the
old debug cache. No performance improvement is claimed from that size.
