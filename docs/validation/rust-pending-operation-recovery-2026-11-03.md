# Explicit recovery of a pending library operation

Automatic directory-swap recovery continues to handle states it can prove. Previously, an ambiguous restore or rollback stopped startup with an error before the recovery window. Startup now locates the blocked operation in the original or selected imported store and opens the existing independent recovery window before loading the library or PDF engine.

The user can review the current library or select a previous sibling safety folder. Both choices show validated counts and require confirmation. Keeping the current library archives the pending record without moving library folders. Selecting a previous library archives the record and uses the existing whole-folder rollback with a fresh transaction journal. The complete current library becomes a new safety copy. Neither choice interprets paths embedded in the old operation record. The old record is retained, including when its contents are unsupported or damaged.

Review freezes the active folder tree, the selected previous folder where applicable, and the operation record's Windows identity/version and SHA-256. Preparation and installation revalidate them. The record is renamed through its held Windows file handle without replacing a destination. Cancellation before that step changes nothing. After archival, the small installation handover is noncancellable. A failure before a new rollback transaction starts leaves the current store and previous folder in place, with the old record archived. Existing rollback recovery governs an interrupted new transaction.

Whole-store review now copies both the main SQLite file and a nonempty WAL into a temporary directory. SQLite validates that independent copy and produces counts there. A bounded streaming check verifies complete WAL framing, database page size, header/frame checksums and salts against the [SQLite file-format specification](https://www.sqlite.org/fileformat2.html#wal_file_format). This is deliberately conservative: a truncated tail or frames left from a WAL reset require separate recovery. They are preserved, not truncated or ignored. No original SQLite sidecar is created by review.

Executed evidence:

- Three native scenarios build independent synthetic v11 stores in Unicode directories. The active store has three books, including a committed record present only in a real WAL; the previous store has two books. An unconfirmed version-one restore record reaches the actual explicit-recovery branch.
- Each scenario first verifies rejection of a modified WAL checksum, a changed operation record, cancellation before resolution, a changed active tree and two simultaneous operation records. The original files are then checked by complete SHA-256.
- Confirming the current library preserves every active and previous file hash, archives the exact journal bytes and permits the next `recover_and_select` call.
- Confirming the previous library preserves its complete file inventory in the active location and the former current inventory, including its WAL and unknown resource, in the new safety folder. The next selection succeeds.
- Leaving the review without confirmation preserves both libraries and the pending record byte for byte.
- Native images cover English regular and Spanish 640×480 with 200% text. The four actions remain inside their clips; the context and selected-library summary scroll in the compact window. The existing JSON recovery view at 200% has byte-identical RGBA pixels against the prior executable.
- Workspace Clippy across all targets with warnings denied and formatting checks pass. The retained `replacement_keeps_complete_safety_store_and_cancel_does_not_write` test passes, including its existing child-process interruption checks and rejection of an invalid WAL. Its first attempt failed to persist a temporary file in the sandbox's default temporary directory; rerunning with `TEMP` and `TMP` inside the writable verification directory passes. No standalone test cases were added.

The [result artifact](artifacts/pending-operation-recovery.json) records the final executable hash, native outcomes and scoped checks. Reproduce a scenario with `yamantaka-rust.exe --demo --interrupted-recovery=current|previous|cancel --capture=<image.png>`. Add `--es --text-scale=2` for the compact Spanish profile. Synthetic stores and images remain local under `build/`.

This does not certify physical picker/keyboard/Narrator behavior, concurrent external writers, power-loss durability, all WAL histories or installed-library timing. The path requires an existing active folder and a single operation record within 64 KiB; multiple records, missing folders, damaged selection metadata and broader historical recovery remain pending. Final rewrite and Release acceptance are still open.
